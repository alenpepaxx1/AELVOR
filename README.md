Navigation action labels shrink alongside badges and retain full tooltips in the collapsed rail. Touch composer buttons restore 44-pixel targets; at narrow widths the mode selector uses its icon with a complete accessible label. Customize/context panels use bounded scrolling, and opening context closes Customize to reduce vertical competition. These layout corrections pass the automated suite; physical touch, keyboard and browser layout remain unverified.

**Careful local answers:** Settings → Local answer quality offers the default streaming mode or an optional draft followed by one self-review using the same loaded CPU/GPU model. Both passes retain the existing context, output, hardware and phone limits. The full current question, evidence and quoted draft must fit; otherwise review is skipped. Truncated drafts are not reviewed, incomplete/failed reviews retain the completed first draft, and a failed review unloads the interrupted runtime before another AI request. Stop cancels either phase; hidden draft/review tokens still reset the generation watchdog. Only the chosen final answer is displayed. Metrics count the displayed pass and overall elapsed time; this is not independent verification or newly trained weights, and answer-quality improvements have not been benchmarked on physical devices.

Pure explicit numeric expressions such as `Calculate 18 percent of 250` or `Berechne (12 + 8) / 3` get bounded, exact rational arithmetic without arbitrary code execution or network calls. Local tools display the computed result directly; AI Chat receives a quoted arithmetic record if it fits. Supported syntax is decimal-point numbers, parentheses, unary signs, `+ - * / ^`, `× ÷` and postfix `%` (divide by 100). Commas, units, factorials and word problems are not evaluated. Limits are 240 expression characters, 16 digits per number, 128 tokens, 64 operations, 16 parentheses levels, integer powers from −16 to 16 and 192-digit rational components. Decimals are rounded to 12 places and marked approximate when needed; the exact fraction is retained.

Each new AI answer records unfinished fenced code blocks and `[K1]`–`[K999]` labels unavailable in that reply's selected knowledge context, excluding code fences. The expandable EN/DE answer-check panel explains the limits, attempted passes and available arithmetic record. These checks do not prove facts, source correctness or executable code. Bounded metadata survives refresh, branching and conversation backup without storing hidden draft/review content as additional messages.

The interface uses graphite surfaces, mint accents, a geometric monogram and a focused conversation composer. The bilingual prompt library offers everyday, code and security starting points; selecting one fills the composer and selects the appropriate response engine without sending automatically. Desktop navigation can collapse, Studio opens alongside the conversation, and narrow screens use the mobile layout. Existing conversation storage keys, custom models and previous download paths remain compatible.

## Start a natural conversation

1. Open **AI Chat** in the navigation or the activation banner.
2. Choose Qwen 1.5B (default), 0.5B (compact) or 3B (larger), or open **Full model library** to search 159 supported text-model records. Review the device check and press **Download & load selected model**. The app does not download model weights before this action.
3. Allow the first download and initialization to finish. Models require a compatible WebGPU browser/device, roughly 1.0/1.9/2.9 GB of GPU memory, and approximately 0.4/1.0/1.9 GB of model downloads respectively. Download sizes are estimates; device overhead and disk caching vary.
4. Close the panel and send an English or German question about everyday topics, technology, cybersecurity, writing, learning or code. Follow-up questions use a bounded part of recent history.
5. Use **Voice** for speech input and spoken replies, or enable automatic reading in settings. Spoken language is selected from the generated prose, ignoring code blocks.

All three model IDs are real presets from the installed `@mlc-ai/web-llm` 0.2.86 runtime. FP32 variants avoid requiring the optional shader-f16 feature. WebLLM runs in a dedicated worker using the explicit Vite worker import, preserving UI responsiveness. It downloads the selected model from Hugging Face and its compatible compiled runtime from the MLC GitHub repository, then performs inference locally. Browser caching may save repeat downloads, but initialization is still required after reopening. Unload releases the worker/GPU; the model panel can delete selected-model cached files without deleting chats.

These are pretrained Qwen models; AELVOR does not claim to have trained a general language model from 96 classifier examples. They can produce natural conversation across topics, but cannot correctly answer every possible question, browse live sources, execute code, or provide human-level intelligence. The model panel discloses these limits and reports missing WebGPU, memory, download/cache and runtime errors. It never marks AI Chat ready until model loading, file-size verification and a short local response test succeed.

Generation is streamed, cancellable, and bounded to 768 output tokens. A length-limited response exposes a Continue button. We send a fresh system prompt, at most four complete recent user/assistant pairs, and the current question within a 6,000-character conversation budget. The system prompt is additional. Token/character ratios vary, so very dense inputs can still exceed the selected model's context window (up to 4,096 tokens in this app) and produce an explicit shorten-input error. Each generation resets the runtime conversation before submitting this bounded history, preventing hidden context from leaking between chats. Omitted context and shortened file excerpts are disclosed. Historical demos, errors, stopped replies and untrusted system/tool roles are excluded. Stopping preserves already-streamed text.

## First-visit setup

New users choose a username (step 1/2), then choose AI Chat or the built-in local assistant (step 2/2). AI Chat reuses the full GPU/CPU model catalog, device checks, NVIDIA requirement and actual readiness test. Entering with an active model requires that the loaded, tested model match the selection. An explicit Load later action saves the choice and enters with no loaded language model; the normal chat activation guard remains in force. The built-in path uses local tools and the small topic classifier without a language-model download, with its narrower capabilities stated on screen.

Choosing the built-in path cancels any pending model load. Completing that path or choosing Load later releases an old loaded model, preventing a previous GPU/CPU runtime from serving a newly selected model by mistake. A pending profile resumes at the model step after refresh. Model/engine settings are written before clearing the pending marker; partial storage failures keep setup pending for a future visit while allowing the current visit to continue honestly. Existing version-1 username profiles remain compatible. Settings includes Review startup AI choice to reopen the flow. Chats, drafts, projects and classifier weights are preserved. Workspace keyboard shortcuts stay inactive during setup.

## Conversation workspace

**Draft recovery and save failures.** Drafts have their own read guard: missing storage permits the first save, while unreadable JSON, unsupported draft versions, invalid top-level containers, blocked access and oversized saved data pause draft writes without replacing the original. Conversation history can still save independently. Settings can download the original draft text and explicitly replace it with drafts from this session. Storage quota/write failures remain visible in the workspace with Retry saving and an export shortcut; copy unsent text before closing because conversation backups exclude drafts. A failed confirmed replacement keeps draft saving paused until a successful replacement or reload. The interface does not label failed saves as saved.

**Saved workspace recovery.** If the workspace snapshot cannot be read, is invalid JSON, or has invalid top-level conversation/project containers, the app pauses workspace autosave, draft writes and conversation-backup imports. The original saved snapshot is left intact. A persistent banner opens recovery in Settings, where the original workspace text can be downloaded when readable from storage. A separate confirmation can replace the stored workspace and drafts with the current session. Failed replacement leaves automatic saving paused; enabling browser storage and reloading can restore access to a valid original snapshot. This protects the existing data on failed reads; it does not repair corrupted files or include drafts in conversation exports.

**Projects, drafts and AI preferences.** Create or rename a project from the history panel, select it to browse its chats, and use the composer Project selector to assign/move a conversation. Up to 50 projects are stored with the existing workspace. Removing a project keeps its chats and saved answers in All conversations. Branches inherit the source project. Search includes project names. Conversation backups optionally include projects while retaining the existing version-1 format: legacy backups still import; project IDs are remapped safely, and case-insensitive matching names reuse an existing project. Empty projects can also be exported/imported.

Unsent text and up to three text attachments autosave after 250 ms and flush when the page is hidden or closed. Navigation saves the outgoing draft before restoring the selected conversation's text, files, mode and engine. The new-conversation draft is shared across projects. Up to 50 recent drafts are kept under `aelvor-drafts-v1`; oversized/unavailable storage is reported. A successful send clears only the submitted draft. Branching preserves the original draft, and deleting a conversation removes its draft. Discard removes the current draft; clearing all history also clears drafts. Drafts are local working data and are excluded from conversation backups.

Settings offers Balanced, Concise and Detailed response preferences plus up to 1,000 characters of custom instructions. Preferences use the separate `aelvor-assistant-preferences-v1` key and guide new AI Chat replies, including regenerated answers, refinements and continuations. Reply-language and library-selection preferences also apply to deterministic Local tools; generation style, custom instructions and format preferences apply to AI Chat. Custom instructions are quoted beneath the core assistant rules; they do not enable browsing or code execution or train the model. Personalization consumes the prompt's character budget before older history is selected. Model adherence and answer quality still vary. Preferences and the local username are excluded from conversation backups.

### Adaptive local responses

The Adaptive, Precise and Creative approaches control actual sampling settings in both WebLLM GPU generation and the CPU worker. Adaptive recognizes bounded English/German task cues: code, security, calculations, writing, investigation, learning, translation, communication and planning. Technical tasks and translation use lower temperature; writing allows more variation. Explicit translation requests take precedence over an inherited subject. Natural follow-ups such as “Could you explain that in more detail?” and “Kannst du das genauer erklären?” retain the earlier subject; new topics remain independent. Precise/Creative override automatic sampling. Concise style lowers the requested output cap to 256 tokens; phone and CPU caps remain authoritative. Older saved preferences default to Adaptive. These are inference controls and task instructions, not new training, a benchmarked intelligence improvement or a factual verifier.

Attachment prompts search the supplied text with a bounded local lexical ranking. They select relevant contiguous excerpts instead of always taking the file prefix, preserve the original bytes, and include source line ranges. The system asks the model to cite only supplied ranges and treat excerpts as untrusted data. The original question is never shortened to make space, and file JSON plus preferences still fit the same device character budget. Search covers only the text actually attached (at most the first 12,000 characters), with no web lookup or external embeddings. Clear follow-ups inherit their earlier subject, including through several short follow-up turns.

The GPU setup offers an explicit capacity suggestion from a curated multilingual Qwen shortlist in the installed runtime. It favors larger parameter counts and applies the same feature, memory, software-adapter and phone gates as loading. Selecting a suggestion never starts a download or changes CPU/GPU mode automatically. The ordinary load step still performs fresh device checks and a local response test. This is a capacity heuristic, not an accuracy or speed guarantee. Publisher references: [Qwen3-4B](https://huggingface.co/Qwen/Qwen3-4B) and [Qwen2.5-7B-Instruct](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct).

### Reply controls, context preview and refinements

Settings adds **Reply language** (match the question, English, German), **Answer format** (adaptive, numbered steps, comparison tables), and **Knowledge sources** (relevant excerpts, source-focused, no library excerpts). Older preference records default these fields safely. Explicit current-language/format requests take precedence over preferences. Source-focused mode instructs the model to use supplied evidence, cite exact labels/lines and state missing or conflicting information; it does not enforce or verify factual correctness. Model adherence varies. Format preferences preserve complete code and strict JSON. No library excerpts disables library retrieval, while explicitly attached files remain available. Source snapshots and response text remain in their original conversations.

The composer's **Context** button previews the shared CPU/GPU preparation before sending: detected task, preferred reply language, retained earlier question/answer pairs, selected knowledge snapshots, and current question/file excerpts. It shows serialized conversation/preference characters within the existing device budget, not measured tokens, memory or the whole system prompt. Preview preparation is deferred while typing and performs no model call, download or network request. The runtime can still reject dense input or reduce older pairs further. Code-project instructions added to the chat draft are included in this same preview. Local tools show their scope and available input/source counts rather than claiming to have generated an AI prompt.

Completed AI replies offer **Refine**: explain simply, shorten, give an example, translate to German or translate to English. Each action branches from the selected response with its original question/answer and earlier context. Later messages and unsent draft attachments stay outside the new request. The source conversation, bookmarks and draft remain available. Copied evidence/attachments are detached from their originals. Stopped, failed, pending and demo answers cannot be refined. Refinement requires a loaded model and preserves the selected pair under the existing context limits; it can fail before creating a branch if the pair does not fit. The existing length-limit Continue operation retains its separate restrictions.

**Local tools document answers** retrieve original passages from TXT/Markdown/CSV/TSV/JSON attachments and enabled knowledge notes. A relevant plain-text question no longer receives log-count metrics by default; explicit log analysis and source-code review retain their dedicated tools. English/German summary requests rank real paragraphs by bounded lexical coverage, return up to three extracts (one in Concise mode), preserve source order and exact line/date metadata, and label the result as an extractive summary. They do not paraphrase, infer new facts or establish that all relevant passages were selected. Missing evidence produces a clear source request in source-focused mode. Explicit previous-answer summaries retain the old answer rather than silently substituting edited library text. Historical excerpt snapshots are saved with tool replies as well as generated replies, and voice uses the selected reply language. Source content is quoted with fences that remain valid when the source itself contains backticks.

These additions improve context preparation, source access and user control in the existing pretrained CPU/GPU models and the separate deterministic local engine. They do not create or retrain language-model weights, give the model autonomous web retrieval, bypass device limits or establish measured quality gains. Tests exercise preference migration/storage failures, multilingual language precedence, both prompt paths, context budgets/omissions, refinement boundaries, isolated source snapshots, extractive range accuracy, quoted hostile text and EN/DE server-rendered controls. Interactive browser/audio and full model quality still require device testing.

### Reusable local knowledge

**Knowledge library** is available from navigation, the composer and Settings. Add/edit a note or import TXT, Markdown, CSV, TSV, JSON and LOG files. Optional source URLs and dates identify user-supplied material; manually saved URL labels are not fetched, and dates are not independently verified. Use Read a web source for an explicit public-page fetch and review before insertion. Up to 24 sources, 40,000 characters per source and 320,000 total text characters are supported. Imports accept at most five text files at a time, each up to 200 KB; oversized, binary, unsupported and unreadable files are rejected without silently truncating the accepted text. PDF/Word files must first be exported as text.

Enabled sources are searched locally for each new AI Chat question, including regenerations and continuations. Bounded lexical ranking uses normalized terms, a small English/German vocabulary and exact contiguous source ranges; it is not semantic embedding search. Up to three relevant excerpts fit within the existing device context budget, counting their serialized JSON. Current questions, supplied attachments and protected continuation pairs take priority. Short natural follow-ups reserve recent dialogue before adding more retrieved context. Older source copies can be omitted with a context-shortening notice to retain the complete question/answer pair. No knowledge content enters a system role, and excerpts are explicitly untrusted data. Generation receives the same rendered evidence through CPU and GPU paths; context, output, phone, hardware and memory limits are unchanged.

Responses keep a **Knowledge context selected** record: exact excerpts, title, line ranges and optional source date/link. The model is instructed to cite these turn-specific `[K1]`–`[K3]` records, distinguish source claims from its explanation, flag conflicting evidence and avoid invented updates. The UI does not claim that a citation is verified or that every excerpt was used correctly. Saved source snapshots survive document edits/removal, refresh, branching, conversation backups and Markdown export. Removing or disabling an individual source does not erase earlier snapshots. Selecting **No library excerpts** omits both new retrieval and replayed excerpt snapshots from future AI preparation; previous answer text can still mention those sources.

The library uses the independent `aelvor-knowledge-v1` browser-storage key. Changes remain active for the visit when saving fails, with retry/export controls and notice that the old saved library can return after reload. Corrupt data is not automatically overwritten on read. Its separate versioned JSON backup merges sources, skips exact copies, remaps colliding IDs and fails atomically at capacity. Conversation backups include only reply-associated snapshots, not the entire library. This provides a way to supply newer material from any field; it does not train new model weights, update pretrained knowledge automatically, give the model autonomous web access or guarantee answer quality. Local tools also search enabled user knowledge for original passages, alongside their authored notes and deterministic operations.

On the first visit without a valid local profile, AELVOR opens a dedicated EN/DE username screen before exposing the workspace. Users choose a 2–24-character handle, with letters, numbers, dots, underscores and hyphens; German letters and normalized Unicode names are supported. The handle and derived initials replace the fixed author identity in the sidebar, user messages and Markdown conversation exports. Settings includes the same validated username editor. Copyright and author attribution remain Alen Pepa.

Profiles use the separate `aelvor-profile-v1` browser-storage key, so changing a username, importing conversations or deleting history does not overwrite the profile or other data. A valid profile skips onboarding on later visits in that browser. Malformed or unsupported saved profiles return to username selection. If browser storage is unavailable, the selected name remains usable for the current visit and a notice explains that it may need to be chosen again. This is a local display profile; usernames do not create accounts, change Site access or claim global uniqueness. Workspace keyboard shortcuts stay disabled until the name is chosen.

Conversations can be pinned above recent chats and renamed from the history or conversation heading. Both preferences survive refresh and are included in portable backups. Search (`Ctrl/Cmd+K`) matches titles, messages and attached text, with separate All, Pinned and Saved-answer filters. Results show matching excerpts and highlight literal search terms; selecting a message match scrolls to that message and marks it briefly. Search remains local and displays up to 50 results. Saved-answer navigation uses the same render-aware message jump.

Use **Edit in a new branch** beneath a question to revise it, or **Try another answer in a new branch** beneath a response to retry its own question. Both use the currently selected response engine and mode. A new conversation receives only the history before that question, the selected question's text attachments and the revised/retried question. The answer being replaced and all later turns stay out of the new prompt. Original conversations remain untouched; copied messages receive new IDs and do not duplicate saved-answer bookmarks. The branch records its source conversation and appears with a branch icon. AI readiness and input/context validation happen before a branch is inserted. Generation retains the existing streaming, cancellation and GPU safeguards.

Settings includes **Export backup** and **Import backup** for versioned `aelvor-conversations` JSON. Backups include conversation messages, text attachments/excerpts, pins, saved flags and measured response metadata; they do not include model weights, classifier datasets, API keys or browser preferences. Pending replies are exported as stopped snapshots without interrupting the live response. Import validates format/version, IDs, roles, content types and bounded counts before offering a preview. Maximum input is 10 MiB, with a combined-history limit of 2,000 chats and 50,000 messages. Markdown conversation export remains available separately.

Import adds conversations without replacing existing history. Content-identical copies are skipped even after a previous import remapped their IDs. Conflicting IDs receive new chat/message/attachment IDs and branch-parent links are remapped, including links to parents skipped as duplicates. The merged history must be saved successfully before React state changes; a quota or storage failure leaves the existing workspace in place. Backups contain user text and should be stored in a trusted location. New regression tests exercise round trips, snapshot recovery, hostile/malformed input, ID collisions, repeated imports, parent remapping, branch prompt boundaries, pin persistence, bilingual search, attachment search and literal highlighting. Real browser layout/audio and GPU inference are still outside the available verification environment.

### Public web references and Windows commands

**Knowledge library → Read a web source** explicitly fetches public HTTPS documentation/reference pages from the fixed host list shown in the panel (Microsoft Learn, Python, Node.js, MDN, Chrome, React, TypeScript, OWASP, GitHub Docs, Git, Android, Apple, Flutter, RFC Editor and English/German Wikipedia). It is a URL reader, not unrestricted web search or an arbitrary proxy. Only the entered URL is sent upstream; chat text, attachments, model data, browser credentials and companion tokens are not forwarded. Unknown hosts, private addresses, credentials, nonstandard ports and secret-like query keys are rejected. Redirects must remain on supported hosts. The same-origin POST endpoint uses private/no-store responses, a 20-second deadline and a 1 MiB streamed-byte cap. It accepts UTF-8 HTML/plain text/Markdown/JSON, extracts text while omitting scripts, styles and selected navigation regions without executing HTML, and clips the saved copy at 40,000 characters with an explicit notice. Dynamic/sign-in/paywalled/blocked or unsupported pages can require pasted/exported text instead.

Read results show title, final URL, retrieval time and extracted text before **Add to knowledge**. Retrieval time is separate from publication/source date. `retrievedAt` survives validated knowledge backups, response snapshots, follow-up context, extractive summaries and Markdown exports. Excerpt lines refer to the saved extracted copy, not original HTML line numbers. Editing a source manually clears the fetched-copy timestamp. Adding the same title/URL/text refreshes the existing copy's retrieval time without changing its enabled state. Other imported sources merge within the existing limits; failed storage still offers local export/retry. Models use relevant saved excerpts through the existing CPU/GPU preparation; Local tools can quote them as well. No source content is treated as instructions, no background refresh occurs, and source correctness is not verified.

**Windows terminal** is available in navigation and a code project's Build guide. The optional downloadable `/windows/aelvor-windows-bridge.mjs` requires Node.js 22+ on a Windows PC. Run it from a normal local terminal with `--root "C:\Projects\MyApp"` and the app's HTTPS origin. It accepts an existing local-drive project folder, binds only to `127.0.0.1:47321`, prints a random per-process session token and uses no npm dependencies. The app connects only on an explicit click, checks the granular loopback permission where supported, and keeps the token in panel memory, outside browser storage, chat, URLs and server requests. CORS, exact Host/Origin checks, a timing-safe session-token check and bounded JSON input gate every native action. Unknown routes, non-Windows environments and unconfirmed/invalid commands are rejected. It does not install a Windows service, change script policy or grant administrator privileges.

Choose Windows PowerShell or CMD/Batch, review/edit a command, choose 30/60/180 seconds, confirm that command and select **Run on Windows**. Presets offer tool versions, folder listing, Git status and checks for authored project scaffolds; imported projects do not receive invented npm/test commands. The companion runs one command at a time with the user's existing Windows permissions. Its root is an initial working directory, not a filesystem sandbox. Browser sources are not synchronized with Windows files: export the provided Project ZIP, extract it into the chosen Windows folder, then run checks there. iOS/Xcode builds retain their macOS requirements. Interactive programs and persistent development servers belong in a normal terminal.

PowerShell receives exact UTF-16LE encoded command text with UTF-8 output settings. CMD uses a temporary UTF-8 batch file, `/d /s /c`, a fixed environment-variable path and `shell:false`; temporary files are cleaned after execution. Source text is submitted as an intentional command only through the reviewed Run action, never from AI replies or web-source extraction. The runner caps output at 128 KiB and requests Windows process-tree termination on timeout, output overflow or cancellation. Cleanup failure is reported and blocks subsequent runs until the companion is restarted after manual process inspection. Accepted run IDs are never replayed in that companion session (up to 1,024 IDs, then restart is required). Connection errors never retry a command or imply that it stopped. Closing the panel requests cancellation only for commands started by that panel; network failures can prevent confirmation. Reconnecting can recover an authenticated active command ID for an explicit stop request, without repeating the command or recovering earlier output. Observing a command started elsewhere never makes it eligible for automatic cancellation on panel close. Older companion versions without active IDs remain compatible, with manual/original-panel cancellation when an ID is unknown. Download the updated companion again and restart it for the reconnection and timing fixes. Keep the local terminal available to inspect the actual Windows state.

Results show stdout, stderr, elapsed time, status and exit code. **Add result to AI chat draft** appends bounded, Unicode-safe quoted JSON to the existing draft for review; it does not send automatically or run proposed follow-up commands. The model is told to identify PowerShell/CMD syntax and distinguish observed output from unrun tests or scans. Captured output can contain private data and older programs can ignore UTF-8 settings, so inspect it before including it in chat.

Tests exercise host/redirect/size/type/origin guards, exact text extraction and provenance, companion authentication/preflight/replay/concurrency/cancellation boundaries, native invocation arguments, temporary-file cleanup, the real child-process capture path with controlled Node subprocesses, client failure/no-retry behavior, prompt budgets and EN/DE server-rendered controls. The build verifies that the companion download matches the reviewed source. Native Windows PowerShell/CMD, browser loopback permissions and hosted upstream access require device/deployment QA; the Linux fixtures do not establish their behavior. Browser policies or embedded frames can block loopback access; copy/download commands remain available. Public source availability can change.

## Model library and device checks

The library is generated from the installed WebLLM 0.2.86 package with `node scripts/export-model-catalog.mjs`. It includes all 159 text LLM records, including Llama, Qwen, Phi, Gemma, Mistral and other families. Vision and embedding records are excluded. Search by name or exact model ID, filter by family, and optionally hide records whose requirements are not met. Selecting a record does not download it. Source-file and license links point to its actual publisher repository. Arbitrary Hugging Face checkpoints and GGUF files are not compatible with this runtime.

The selection panel and the runtime both check the device. The runtime uses a fresh check on every load, before creating the inference worker or fetching model weights. Missing WebGPU/workers, unverified GPU checks, missing GPU features (including inferred FP16 requirements), and insufficient runtime-wide GPU limits prevent loading. WebLLM 0.2.86 requires at least 256 MiB maxBufferSize, 128 MiB maxStorageBufferBindingSize, 32 KiB workgroup storage and 10 storage buffers per shader stage. Model buffers are checked against the device limits the SDK actually requests: 1 GiB where supported, otherwise 256 MiB buffers and 128 MiB storage bindings. Adapter maxima between these tiers do not imply that the runtime can use those larger buffers. Optional GPU-label and CPU/RAM metadata failures are isolated from the rest of the device inspection. CPU logical-thread counts are advisory; they do not measure CPU speed. A separate CPU-only WebAssembly SIMD backend is available in AI Setup → CPU compatibility. It does not depend on WebGPU or a GPU vendor.

Memory planning is explicitly conservative: GPU budget = SDK VRAM estimate × 1.2, rounded up to 0.1 GB; RAM budget = max(4 GB, ceil(SDK GPU estimate × 1.5 + 2 GB)). These are application heuristics, not measured consumption, minimum manufacturer specifications or a guarantee of fit. Models with GPU planning estimates above 3 GB require a declared GPU budget. When RAM is unreported, estimates above 2 GB GPU planning require a declared RAM budget. A coarse browser RAM estimate below the RAM planning estimate blocks loading until a smaller model or a known RAM budget is selected. Browser RAM estimates can be capped; entering known budgets avoids treating those caps as the computer's physical capacity. Budgets are saved with model preferences; old settings remain readable.

Web browsers do not provide dependable free-RAM/free-VRAM readings here. The GPU buffer limit is an allocation limit, not total GPU memory. For shared GPUs, the user must budget for system RAM shared with the OS and other apps. The displayed browser-cache quota is a storage estimate, not available RAM or OS disk space. Browsing shows approximate download sizes for the original three suggestions only. Activation reads the publisher's tensor manifest and displays declared weight bytes for the selected model, excluding tokenizer/runtime files. Sizes are never inferred from VRAM. Initialization and runtime allocation can still fail after preflight, and failures/cancellation are surfaced without marking the model ready. Model-specific 1K/2K context caps are preserved; larger caps are limited to 4K, and output is bounded to half the configured context or 768 tokens, whichever is smaller.

After the resource gate, `model-download.ts` checks the selected SDK record's config, optional model-package manifest, supported tokenizer and tensor-cache manifest. Metadata is bounded to 16 MiB; model-part paths must stay inside the publisher's model directory, declared byte counts must be safe integers, parts must be unique and tensor byte ranges must fit their shards. Corrupt cached metadata is evicted and fetched afresh. Transient metadata failures retry once with a 30-second deadline per request; missing/denied files do not retry. Catalog browsing does not fetch metadata or weights.

Before SDK initialization, cached weight parts are streamed to count actual bytes without accumulating entire weights in JavaScript. Incomplete or oversized cached parts are removed, leaving valid parts available for the SDK to reuse. After initialization, cached parts are checked again. These are completeness/size checks, not cryptographic weight authentication. The SDK retains its own compiled-model/config compatibility checks and integrity checks where the record provides them. The app uses the installed record's actual compiled-library URL, including libraries shared by multiple variants.

Before Ready, a synthetic request must produce nonempty text within 90 seconds, followed by a chat reset. The exchange never enters saved user history. A failed test disposes the worker; it does not claim anything about answer quality or bilingual fluency. Loading progress stays monotonic and below 100% until the complete lifecycle succeeds. Cache completeness is reported separately from a working in-memory model: browser eviction can require a later download. Only Qwen3 text records use the SDK's explicitly supported `enable_thinking: false` option, keeping their short chat output budget available for answers.

Cache deletion enumerates only the three SDK CacheStorage namespaces and removes the selected publisher-directory keys plus the exact compiled-library URL. It never fetches a tensor manifest and also removes partial/orphaned files when metadata is absent or corrupt. Other model prefixes, app caches and chat history remain. Variants sharing weights or a compiled library may need to download those files again.

## The separate cybersecurity classifier

`public/models/` contains versioned trained weights, 96 authored English/German examples in eight cybersecurity topics, an evaluation report, a model card, and a Python standard-library inference runner. The original v1 weights remain importable.

Hybrid v2 learns word unigrams, word bigrams, and boundary character 3–5-grams. TF-IDF and L2-normalized vectors feed a class-balanced, regularized softmax classifier; its scores are blended with length-normalized Naive Bayes evidence. Training uses seeded SGD with 20/40/80 passes in a cancellable web worker. No external model is downloaded. The policy can abstain for poor vocabulary coverage or ambiguous scores. Positive word contributions explain the linear branch relative to the runner-up, not the entire ensemble or causality.

Input is bounded to 8–500 examples, 2–12 labels, at least two unique examples per label. Exact normalized duplicates are removed and conflicting labels rejected before training. Examples contain 4–2,000 characters; predictions accept up to 20,000 characters.

With at least 16 examples and four per label, seeded stratified 3-fold cross-validation tests each unique example once outside its training fold. Each fold learns its own vocabulary and IDF. Final weights are refit on all examples. The interface shows overall accuracy (rejections count as incorrect), coverage, accuracy among accepted texts, macro F1, per-class precision/recall/F1, a confusion matrix, and the v1 baseline on the same folds. Similar paraphrases/translations may remain across folds. The small authored corpus is not a representative or independent benchmark. See `public/models/MODEL_CARD.md` for the actual measured results, hyperparameters and policy.

Model lab supports JSON editing, training with progress/cancellation, inspected predictions, model weights, full backups with examples, evaluation exports, v1/v2 import and Python export. Imported/restored evaluation claims are discarded; retraining recomputes metrics. Existing custom v1 models remain active until retrained; only the unchanged bundled v1 starter is automatically upgraded, while its old storage key is retained.

## Conversation runtime architecture

- `ConversationSession` owns model loading, immutable observable state, a single active response, cancellation, model identity, late-result disposal and fatal-error recovery. The React `useConversationSession` hook subscribes through `useSyncExternalStore`; the workspace no longer owns SDK worker refs or repeats lifecycle transitions.
- The 15-minute load deadline covers the entire lazy import, GPU probe and model initialization. A generation with no new text for 3 minutes is aborted and the failed runtime is disposed. User cancellation keeps a healthy model available. Neither deadline is a claim about expected performance.
- A FIFO async mutex and `serialGeneration` hold the SDK lease until iterator cleanup finishes. Cancelled queued requests are removed, late stream initialization is closed, and a subsequent reset cannot race old generation cleanup. Disposing a runtime rejects queued requests.
- Only recognized GPU or CPU prompt-context overflow errors are retried, before any rendered text. Each retry removes one complete oldest user/assistant pair, at most four times. The current question, protected continuation pair and system prompt remain intact. After text has appeared, errors propagate without regenerating or duplicating that text.
- Response details use measured browser elapsed time and time to first text, plus runtime-reported completion/prompt token counts and decode speed. No word-count estimate is shown as a token count. Details and actual context retry counts survive history restoration; malformed metrics are discarded.

The lifecycle, synchronization and overflow tests inject controlled runtimes so races can be reproduced without a GPU. Real GPU inference, browser layout and audio still require device-level verification. The pinned model family and model weights have not changed; this release improves application code rather than claiming a more intelligent model.

## CPU and GPU hardware paths

AI Setup now offers **GPU acceleration** and **CPU compatibility**. GPU mode uses the existing WebLLM catalog and validates WebGPU features and allocation limits regardless of NVIDIA, AMD, Intel, Apple or an undisclosed GPU vendor. GPU names are labels, never compatibility gates or VRAM measurements.

CPU mode uses pinned Transformers.js 3.8.1 with ONNX Runtime Web, q8 ONNX exports of Qwen2.5 0.5B (512,096,557 weight bytes; 4 GB RAM planning) and 1.5B (1,578,954,293 weight bytes; 8 GB RAM planning). Each has a pinned publisher revision. Intel, AMD and ARM processors use the browser's WebAssembly implementation; there are no native CPU-vendor binaries or required API keys. WASM SIMD and workers are mandatory. CPU budgets are checked again before every load; a hidden RAM estimate requires a known budget. The conservative RAM estimates do not measure free memory and cannot prevent every browser allocation failure.

CPU execution runs in its own worker. Cross-origin-isolated contexts may use up to eight logical threads; other contexts use one inference thread without blocking the interface. This hosted page does not promise cross-origin isolation or full CPU-core utilization. Stop terminates the CPU worker promptly and clears readiness; loading again reuses valid cached model files. GPU cancellation behavior is unchanged.

CPU and GPU downloads have separate formats and caches. CPU cached weights are counted with bounded streaming reads; truncated or malformed cached files are evicted. A local response must succeed before Ready. CPU WASM assets are copied from the pinned dependency to same-origin static assets by `scripts/prepare-cpu-runtime.mjs`; package licenses and third-party notices are retained. No models are downloaded by opening the selection panel.

The automated suite validates capability gates, vendor-independent GPU assessment, CPU streaming/cancellation, cache recovery and resource failures with fixtures. Actual model-answer quality, browser CPU speed and physical AMD/Intel/NVIDIA driver combinations require real-device testing. No universal hardware or performance guarantee is made.

## iPhone and Samsung phone profiles

The app recognizes broad iPhone, iPad, Samsung/Android and other mobile hints. It never infers a specific SoC, model generation, physical RAM or GPU support from the name. The same live WebGPU and WASM/SIMD gates remain authoritative. Apple, Adreno, ARM Mali/Immortalis and Samsung Xclipse labels are displayed without vendor-based allowlists. Actual drivers and browser exposure determine compatibility.

New phone installs start with compact Qwen 0.5B GPU selection. AI Setup offers one-click phone GPU/CPU presets without starting downloads. GPU presets prefer compatible Qwen 0.5B FP16, then FP32; lower-memory SmolLM2 variants remain an alternative. CPU presets prefer Qwen 0.5B when RAM is known and sufficient, otherwise pinned SmolLM2 135M q8 (135,658,354 weight bytes). The 135M model primarily supports English; Qwen remains the choice for German and better language quality. It is a genuine generative model, not a lookup or classifier.

Phone runtime limits use at most 2,048 context tokens, 2,400 prompt/history/preference characters, 256 GPU output tokens or 128 CPU output tokens and at most two CPU inference threads where browser isolation allows threading. Smaller original context limits remain intact. The runtime rechecks the phone profile on every load and passes limits to the GPU/CPU worker. Prompt limits never silently truncate the current question or drop a protected continuation. Desktop limits are unchanged.

App planning ceilings are conservative policies, not measured memory: iPhone/unknown phones allow at most 1.5 GB of GPU planning and 750 MB CPU weight files; Samsung/Android/iPad profiles allow at most 3 GB GPU planning and 1.6 GB CPU weight files, with the usual model RAM gates. Entering large RAM/VRAM budgets does not bypass these ceilings. When RAM is undisclosed, only the small 135M CPU model can be attempted with an explicit caution; larger CPU models still require known RAM. Loading and its real local-response test can fail even after checks.

An optional phone-only background policy stops active replies/loads and unloads model memory when the page becomes hidden; downloaded files and history remain. It does not restart AI or downloads automatically on resume. The setting is stored with existing conversation preferences. Keyboard-aware viewport sizing, safe-area padding and larger touch controls improve use in mobile browsers without disabling pinch zoom.

Browser guidance is grounded in the [Safari 26 release](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) and [Chromium WebGPU support](https://developer.chrome.com/docs/web-platform/webgpu/overview/). Embedded browsers and Galaxy chipsets differ. There is no bypass for unavailable WebGPU, disabled browser features or insufficient memory. Physical iPhone/Galaxy execution, sustained temperature behavior and touch layout require real-device QA; automated tests use capability, lifecycle and rendering fixtures.

## Desktop/laptop GPU preference

### OS hardware inventory and memory provenance

The device panel distinguishes browser logical-processor hints, approximate/capped RAM, the active WebGPU name and unexposed VRAM. It never presents a GPU buffer limit or shared system memory as dedicated VRAM, and does not infer CPU names or memory capacity from device marketing names. Browser GPU names retain up to 256 characters. Full hardware detection cannot be guaranteed by a web page or by drivers.

An optional read-only Windows collector is downloadable at `/hardware/aelvor-hardware.ps1`. Run the reviewed script in 64-bit PowerShell, under the machine's normal script policy, then import its new JSON file in AI setup. It reads CPU names/cores through CIM, installed memory-module bytes, OS-visible/available RAM and DXGI adapter descriptions. Dedicated/shared GPU memory uses pointer-sized 64-bit values; legacy 32-bit GPU memory values are not used. CIM-only fallback GPU entries retain unknown memory. No system settings, script policies or drivers are changed; the only persistent action is creating one new local report file. It performs no network upload and does not export host/user names, serials or adapter-unique IDs. Windows/PowerShell execution remains unverified in the Linux development environment.

Reports are bounded, schema-validated, allowlisted and saved only in browser storage when available. CPU/GPU names and OS-reported capacities are shown as an imported snapshot, separately from browser measurements and the actual model-worker GPU. Other operating systems and phones retain browser checks/manual budgets; a Windows report cannot apply their budgets. Imports never switch graphics processors or bypass GPU feature, memory, software-adapter or phone gates.

Applying reported RAM uses the available-memory snapshot when present, without claiming it is currently free. Applying GPU memory requires a unique exact normalized model-name match between DXGI and the active WebGPU adapter. Vendor-only names, identical-card ambiguity, software adapters and unreported capacity disable automatic GPU budgets. Shared memory is never added. A report-derived VRAM budget is linked to that browser GPU name and checked again before download and against the loaded model-worker label before readiness. A switch to Intel cannot reuse an RTX budget. Explicit manual budget selection removes the link. Imported snapshots are user supplied, not cryptographic attestations; live allocation and the local response test remain authoritative.

References: [DXGI adapter memory fields](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc1), [adapter enumeration](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgifactory1-enumadapters1), [CPU model reporting](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor), [physical memory capacities](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-physicalmemory) and [Chrome's approximate device-memory API](https://developer.chrome.com/blog/device-memory).

AI setup now has an explicit GPU requirement: Automatic (high performance), NVIDIA (RTX/GTX), AMD or Intel. The default remains vendor-neutral. The choice is persisted under the existing conversation settings key and applies only to GPU loads. Changing it unloads an existing GPU model, so the next request cannot reuse a model that was initialized on the previous GPU. CPU mode remains an explicit, independent selection. This is a manufacturer requirement, not an enumeration of installed cards or a guarantee that an NVIDIA adapter is a particular RTX model.

The normal resource gate rejects a mismatched or undisclosed required manufacturer before any model metadata/download or model worker starts. After loading, a second check uses the pinned WebLLM 0.2.86 terminal `Finish loading on WebGPU` report. Its label comes from the adapter whose device initializes inference in the model worker. An Intel/unknown worker under an NVIDIA requirement is terminated before the local readiness reply test and never becomes Ready. Known software adapter reports are rejected as well. The active model's GPU label is shown separately from the current browser probe. The SDK's `getGPUVendor()` requests another adapter and is deliberately not used as proof of the loaded device.

WebGPU `powerPreference: high-performance` is a hint; browser/OS routing can still return Intel. A website cannot select an otherwise hidden RTX card by name. The EN/DE GPU panel now precedes technical device details and opens activation help for unavailable/software adapters, incomplete identity, known integrated Intel graphics, manufacturer requirements, GPU-specific worker failures and mismatched report-derived VRAM budgets. A pending check does not diagnose stale results. Integrated graphics remain allowed in Automatic mode; Intel Arc and dedicated Iris Xe MAX are not classified as integrated. Unrelated download/context/memory-budget errors do not themselves trigger activation help.

The guide covers browser graphics acceleration, Windows Settings → System → Display → Graphics for the browser/app actually hosting AELVOR, Device Manager and manufacturer driver checks, followed by a full browser/app restart. Automatic mode does not assume an NVIDIA card. Known non-Windows devices do not receive Windows routing steps; phone guidance explains built-in GPUs. A new browser probe never relabels the loaded worker: after routing changes, check again, unload and reload the model. Windows preferences can override NVIDIA Control Panel; VRAM budget changes do not change adapters. An embedded/remote browser may need a locally installed Chrome/Edge configured for the desired GPU. These diagnostics are covered by pure unit and server-rendered EN/DE component tests, not physical Windows/GPU/browser UI verification. References: [WebGPU adapter preferences](https://www.w3.org/TR/webgpu/#dom-gpurequestadapteroptions-powerpreference), [Chrome acceleration](https://support.google.com/meet/answer/9302964?hl=en), [Windows graphics settings](https://support.microsoft.com/en-us/windows/hardware/display-graphics/optimizations-for-windowed-games-in-windows-11) and [NVIDIA GPU routing](https://www.nvidia.com/content/Control-Panel-Help/vLatest/en-us/mergedProjects/3D%20Settings/Setting_the_Preferred_Graphics_Processor.htm).

Computers and laptops start with the WebGPU model backend by default. GPU loads use the installed WebLLM runtime, whose GPU adapter request prefers `high-performance`. GPU failure remains an error; the loader does not attempt CPU models automatically. Choosing a CPU model explicitly remains available and is stored as `cpuExplicitChoice: true` alongside the existing model setting. Legacy desktop CPU settings without that explicit choice return to the GPU default; phone CPU selections remain valid. Choosing a GPU model clears CPU opt-in.

The chat caption and active AI badge distinguish GPU/WebGPU from CPU/WebAssembly using the **loaded** model, even when a different model is selected in setup. Known software WebGPU adapters (reported fallback adapters or identifiable SwiftShader/llvmpipe/Lavapipe/Microsoft software renderers) are blocked before GPU model downloads. Hidden adapter information does not prove a physical GPU is present and is not treated as a vendor failure. The browser and operating system ultimately choose the adapter; physical GPU selection and performance still require device testing.
